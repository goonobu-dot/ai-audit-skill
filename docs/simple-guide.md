# はじめての ai-audit — これって何だろう？

> AIにアプリを作ってもらった。**動いてはいる。でも、中で変なことをしていないか、本当に大丈夫なのか、自分では分からない——**
> このモヤモヤに、正面から答えるための道具です。

コードが読めなくても大丈夫です。このページは、専門用語をできるだけ使わずに「**何の役に立つのか**」と「**どう使うのか**」だけを、順番に説明します。

---

## なぜ今、これが必要なのか

いま、エンジニアでない人でも、AIに指示するだけでアプリや業務システムが作れる時代になりました。とても便利です。でも、こういう不安がついて回ります。

- 🔑 「お客様の個人情報や、パスワード・鍵が、**うっかり外に漏れる作り**になっていないか？」
- 🤖 「**頼んでいない余計な動作**を、こっそりしていないか？」
- 📦 「古くて**危険な部品(ライブラリ)**を使っていないか？」

エンジニアなら、コードを読んで確かめます。でも**非エンジニアには、それが簡単ではありません**。かといって「AIが作ったから大丈夫」と信じるのは危険です。

**ai-audit は、その"確かめる"作業を、あなたの代わりに——しかも一人のAIに丸投げせず——肩代わりする仕組みです。**

---

## この道具のいちばんの肝:「作った本人以外の目」で見る

ここが最も大事なところです。

人間でも、**自分が書いた文章の誤字は見つけにくく、他人はすぐ見つけます**。AIも全く同じで、**コードを書いたAI自身は「ちゃんとできたはず」という思い込みを抱えたまま**チェックするので、自分のミスを見逃します。

そこで ai-audit は、**そのコードを作っていない、別の会社の別のAI**に、思い込みなしで監査させます。これを「**認知的独立性**」と呼びます。難しく聞こえますが、要は「**当事者じゃない第三者に、他人の目で見てもらう**」ということです。

### さらに——AIは「1つより、複数の別会社のもの」の方が強い

そして、これが今回いちばん伝えたいことです。

**別会社のAIを2つ、3つと増やすほど、それぞれ"違う穴"を見つけます。** なぜなら、AIごとに得意・不得意や"見る癖"が違うからです。

これは机上の空論ではありません。**この ai-audit 自身を、3つのAIに監査させたときに、実際に起きたこと**をお見せします。実装したAI(Claude)が見落としていた欠陥を、他社のAIたちが見つけたのですが——**見つけた穴が、AIごとにバラバラだった**のです。

| どのAIが | 見つけた"穴"(実際の例) |
|---|---|
| **Grok(xAI / Cursor経由)** | ・削除の許可判定を、目印ファイル1枚で**偽装**できる穴<br>・危険度「最高(CVSS 9.8相当)」の脆弱性を**「低」と誤判定**して見逃す穴<br>・サンプル画面の行数表示のズレ |
| **Codex(OpenAI)** | ・入力がショートカット(シンボリックリンク)のときの**すり抜け**<br>・**壊れた/偽装された検査結果**を「問題なし」と読んでしまう穴<br>・「全履歴を検査」と表示しつつ、実は**今のファイルしか見ていなかった**穴<br>・中身ゼロの"空っぽの封印"が作れてしまう穴 |

👉 **注目してください。GrokとCodexは、まったく別々の穴を見つけています。** もし1つのAIしか使っていなかったら、この表の半分は見逃されたままでした。さらに最初の監査では、両方のAIが**同じ重大バグ(データ消失の危険など)には揃って警告**しました——重要なものは全員一致、細かいものは手分けして発見、というわけです。

**「複数の、別会社のAIに監査させる」だけで、セキュリティも品質も、これだけ実際に良くなります。** これがこの道具の核心的な価値です。

> ⚠️ **正直な但し書き:** それでもこの道具は「絶対に安全」を保証しません。役目は「**何を調べて、何がまだ未確認か**」を隠さず示すこと。「未検証」を「安全」と言い換えたりはしません。この誠実さこそが価値です。

## AIは何個必要？(2つでもOK、3つが推奨)

「Cursor(Grok)は契約していない」という方も多いはずです。大丈夫です。

| 構成 | 位置づけ |
|---|---|
| **Claude + Codex(2つ)** | ✅ **正式サポート・最小構成**。作った本人以外の目が1つ入るので、認知的独立性は成立します |
| **Claude + Codex + Cursor(Grok)(3つ)** | ⭐ **推奨**。監査役を毎回交代でき、上の表のように"違う穴"がより多く見つかります |
| Claude だけ(1つ) | 縮退モード。独立性がないので、結論を安易に「合格」にしません |

つまり、**まずは2つ(Claude + Codex)で始めてOK**。もっと厳しく見たいとき、3つ目(Cursor経由のGrok)を足すと、さらに見つかる、という設計です。1社しか使えないときは、その事実(監査役を交代できないこと)を報告書に正直に書きます。

## 使い方は、たった3ステップ

### ステップ1｜AIにこのプロジェクトを読ませる

お使いのAI(Claude Code / Codex など)に、こう伝えるだけです。

```
https://github.com/goonobu-dot/ai-audit-skill を読んで、
このスキルをこのプロジェクトに入れて
```

これで AIが `ai-audit`(監査)と `code-atlas`(中身の見える化)を認識します。

### ステップ2｜アプリを普通に作る

いつもどおり、AIにアプリを作ってもらってください。**監査のことは、作っている間は気にしなくて大丈夫です。**

### ステップ3｜作り終わったら、この一言

コードが完成したら、こう言うだけです。

```
コードを監査して、報告書を作って
```

すると、こう進みます。

1. 🔒 **機械チェック** — 秘密の鍵・個人情報・危ない古い部品が混ざっていないか、機械が確認(専用ツールが無ければ「未検証」と正直に返します)
2. 🔍 **別会社のAIによる独立監査** — Codex(と、あれば Grok)が、作ったAIの説明を渡されずに、仕様とコードだけから欠陥を探します
3. 📋 **証拠つき報告書** — 「何を調べ、何を見つけ、何が未検証か」をまとめた報告書が出ます

### いちばん効くのは「通るまで回す」——収束ループ

実は、この道具のもう半分の肝はここです。**検出して終わりでは、コードは良くなりません。** 大事なのは、

**監査する → 出た指摘を直す → もう一度(できれば別のAIで)監査する** を、**重大な指摘が出なくなるまで繰り返す**こと。

これを「収束ループ」と呼びます。回すたびに指摘は減っていき、やがて落ち着きます。実際、この ai-audit 自身も、公開前に**3周**回して仕上げました(1周目で重大バグ→修正→2周目で残り→修正→3周目でさらに細かい残り→修正、と収束)。

> 💡 ひとつだけコツ:**「同じAIが黙るまで」回すと、そのAIの盲点に慣れてしまい逆効果**です。だから「**直す担当**」と「**判断する担当**」を分け、できれば**監査役を毎回交代**します(2社目・3社目がいると効くのはこのため)。テストを甘くして無理に通す、といったことはしません。

> 💡 監査は外部AI(あなたのCodex/Cursorの契約枠)を使う、少し重い工程です。周回が増えそうなときは、AIが先に「この範囲を、だいたい何周みます」と一声かけてから進めます。

## よくある質問

**Q. コードが読めないのですが、報告書を見て意味が分かりますか？**
A. 報告書は「要求 → やった検査 → 結果 → 証拠」の対応表です。さらに `code-atlas` が、中身を図や要点カードで見える化します。「中身を分かりやすく説明して」と言えば動きます。可視化も万能ではないので、追えない箇所(盲点)は緑にせず赤で正直に開示します。

**Q. 私のコードや秘密が、外部のAIに漏れませんか？**
A. 外部AIに渡す前に、**既知の形式の**秘密や個人情報を隠す送信前ゲートを通します。ただしこれは網羅ではありません——未知の形式の秘密や氏名・住所は取りこぼしうるので、送る前に人が中身を確認します。また「コードそのものが機密」なら、値を隠しても外部送信の可否は別問題です。

**Q. 結局、これで「安全です」と言えますか？**
A. 言えません。そして、それが正しい姿です。渡すのは「安全の宣言」ではなく「**調べた範囲と、まだ調べていない範囲の、正直な地図**」。最終判断は人間が行います。
