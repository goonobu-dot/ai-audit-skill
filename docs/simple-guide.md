# 3ステップで使う ai-audit — かんたんガイド

このページは、**コードが読めなくても使える**、いちばんやさしい入り口です。むずかしい設定は後回しにして、「何の役に立つのか」と「どう起動するのか」だけを説明します。

---

## まず、これは何のための道具？

AIにアプリやシステムを作ってもらう人が増えています。でも、こう思いませんか。

> 「動いてはいるけど、**中で変なことをしていないか**、本当に大丈夫なのか分からない」

ai-audit は、その不安に答えるための道具です。作ったAI**自身**にチェックさせるのではなく、**別の会社の別のAI(OpenAIのCodex、xAIのGrok)に、他人の目で監査させます。**

### なぜ「別のAI」なのか — これが肝心です

人間の世界でも、自分が書いた文章の誤字は見つけにくく、他人はすぐ見つけます。AIも同じで、**作った本人(AI)は「ちゃんと繋いだはず」という思い込みを持ったまま**チェックするので、自分のミスを見逃します。

そこで、**作っていない別系統のAI**に、思い込みなしで見てもらう。これを私たちは「**認知的独立性**」と呼んでいます。実際、この道具の開発中にも、別系統AIが「作ったAI本人は気づかなかった欠陥」を何度も、しかも**再現手順つきで**見つけました。その一部は、この道具自身のコードのバグでした。

### 何がうれしいのか(誰にでも分かる言葉で)

| こんな場面 | ai-audit があると |
|---|---|
| AIが作ったアプリを世に出す前 | 秘密の鍵やお客様の個人情報が「混ざっていないか」を、機械のゲートで先に止める |
| 会社や取引先に納品する | 「動きました」だけでなく、**何を・どこまで調べて・何が未確認か**を証拠つきの報告書で渡せる |
| 中身が分からなくて不安 | 何を根拠に判断したのか、専門家に引き継げる形で残る |
| 品質を上げたい | 別AIの監査で問題を洗い出し、直して、また監査、を**問題が出なくなるまで**くり返せる |

> ⚠️ **正直な但し書き:** この道具は「絶対に安全」を保証するものではありません。**「何を調べて、何がまだ未確認か」を隠さず示す**のが役目です。「未検証」を「安全」と言い換えたりはしません。この誠実さこそが、この道具の価値です。

---

## この公開リポジトリに入っているもの

clone するとすぐ使えるのは、次の2つのスキルと、入口の機械ゲートです。

- **`ai-audit`** — 別系統AIによる監査を実施し、要求・検査・証拠・未検証事項を結んだ**技術監査報告書**を作る。
- **`code-atlas`** — 非エンジニア向けに、コードの中身を図や要点カードで「読む代わりに把握」する。
- **`security_gate`(スクリプト)** — 秘密・個人情報・危険な依存を「入る前」に止める機械ゲート。

> ℹ️ 「作り終わったら一言で自動的にループが回る」便利トリガー(`quality-audit-loop`)は、作者の手元環境にある**別の追加スキル**で、この公開リポジトリには**まだ同梱していません**(トリガーの誤爆防止など設計を見直し中)。下の3ステップは、同梱の `ai-audit` だけで成り立つ手順です。

## 使い方は、たった3ステップ

### ステップ1｜AIにこのプロジェクトを読ませる

お使いのAI(Claude Code / Codex など)に、このリポジトリを読み込ませます。いちばん簡単なのは、こう伝えるだけです。

```
https://github.com/goonobu-dot/ai-audit-skill を読んで、
このスキルをこのプロジェクトに入れて
```

これで AIが `ai-audit` と `code-atlas` を認識します。

### ステップ2｜アプリを普通に作る

いつもどおり、AIにアプリやシステムを作ってもらってください。**監査のことは、作っている間は気にしなくて大丈夫です。**

### ステップ3｜作り終わったら、この一言

コードが完成したら、AIにこう言うだけです。

```
コードを監査して、報告書を作って
```

`ai-audit` が起動し、次のことが進みます。

1. 🔒 **機械ゲート** — 秘密の鍵・個人情報・危ない古い部品(依存)が混ざっていないか、機械が止めます(専用ツール未導入なら「未検証」と正直に返します)
2. 🔍 **別AIの独立監査** — CodexやGrokが、作ったAIの説明を渡されずに、仕様とコードだけから欠陥を探します(※この「説明を渡さない独立性」は運用で守るもので、機械が強制するわけではありません。同じチャットで作った直後に監査すると独立性は弱まります)
3. 📋 **証拠つき報告書** — 「何を調べ、何を見つけ、何が未検証か」をまとめた報告書と、封印(seal)が出ます

### 「通るまで仕上げる」には(ループの回し方)

一度の監査で終わりにせず、**問題が出なくなるまで**回すと品質が上がります。手順はシンプルです。

1. 「コードを監査して」→ 報告書を受け取る
2. 指摘を**直す**(直す作業と監査は別々に承認します)
3. もう一度「監査して」→ 前と別の観点/別AIで再監査
4. 重大な指摘が出なくなるまで 2〜3 をくり返す

> 💡 監査は外部AI(あなたのCodex/Cursorの契約枠)を使う、少し重い工程です。周回が増えそうなときは、AIが先に「この範囲を、だいたい何周みます」と一声かけてから進めるのが推奨運用です。

## よくある質問

**Q. コードが読めないのですが、報告書を見て意味が分かりますか？**
A. 報告書は「要求 → やった検査 → 結果 → 証拠」の対応表です。さらに `code-atlas` が、中身を図や要点カードで見える化します。「中身を分かりやすく説明して」と言えば動きます。ただし可視化も**万能ではなく**、盲点(解析できなかった箇所)は緑にせず赤で開示します。

**Q. 私のコードや秘密が、外部のAIに漏れませんか？**
A. 外部AIに渡す前に、**既知の形式の**秘密や個人情報を隠す送信前ゲート(build-prompt-bundle)を通します。ただしこれは**網羅ではありません**——未知の形式の秘密や、氏名・住所などは取りこぼしうるので、送る前に人が中身(transmission-ledger.json)を確認します。また「コードそのものが機密」の場合は、値を隠しても外部送信の可否は別問題です。漏洩対策の道具が漏洩源にならないよう、外部にコードを送る設計のツールは採用していません。

**Q. これで「安全です」と宣言できますか？**
A. できません。そして、それが正しい姿です。この道具が渡すのは「安全の宣言」ではなく「**調べた範囲と、まだ調べていない範囲の、正直な地図**」です。最終的な判断は人間が行います。
