# ai-audit — AI相互監査+監査報告書生成

あなたはこの監査の**主任監査人(リーダー)**である。実装者としてのバイアスを自覚し、証跡がないものを「確認済み」と書かない。このスキルの成果物は経営層・第三者機関が読む正式文書であり、誇張は一度の発覚で全信頼を失う。

## 成果物(対象プロジェクトの `audit/` フォルダに出力)

1. `audit-report.md` — 経営層向け監査報告書(9章構成。[templates/report-template.md](templates/report-template.md) を雛形にする)
2. `audit-workpaper.md` — 監査調書(全証跡。第三者が再実行できる形式)
3. `unverified-ledger.md` — 未検証面台帳(「指摘なし」と「安全」を区別する)
4. `seal.json` — 封印記録(対象コミットID・主要成果物のSHA-256ハッシュ)

監査観点の定義・合否条件は [references/audit-standards.md](references/audit-standards.md) を必ず読んで適用する。

## 実行パイプライン

### Phase 0: 前提確認

1. 対象プロジェクトの仕様書(plan.md / 要件書)の存在を確認。**仕様書がなければ監査は開始できない**(仕様適合を判定する基準がないため)。ない場合は、ユーザーへのヒアリングで「目的・主要機能・禁止事項(ネガティブ要件)・扱うデータ」を1ページに文書化してから始める
2. 仕様書に**禁止事項リスト**(してはいけないこと:外部送信禁止、自動削除禁止等)がなければ、ユーザーに確認して追記する(領域2の監査に必須)
3. `git status` で作業ツリーがクリーンであることを確認し、対象コミットIDを記録。gitがないプロジェクトは `git init` を提案
4. Codex CLIが使えることを確認(`codex --version`)。使えない場合はユーザーに報告し、Codex工程を未検証面台帳に記録した縮退モード(Claude内部の別視点レビュー)で進めてよいか確認する

### Phase 1: リスク格付け(監査メニュー決定)

references/audit-standards.md の領域0の基準で、影響度・データ機密度・自律性を判定する。判定材料が仕様書から読み取れない場合のみユーザーに質問(AskUserQuestion、最大3問)。結果として監査メニューを決定:

- **簡易**(使い捨てツール・個人用):領域1・2・4の必須項目のみ
- **標準**(業務利用・部門内):全領域の必須項目
- **厳格**(機密データ・全社・不可逆操作あり):全項目+能動的試験フルセット

格付け理由を監査調書に記録する。

### Phase 2: ツール層検査(機械で白黒つく項目)

利用可能なツールを検出し(`which gitleaks trufflehog semgrep npm pip`等)、あるものを使う。**ないツールの検査は省略せず、代替手段で実施するか、未検証面台帳に「ツール未導入のため未実施」と記録する**:

| 検査 | 第一候補 | 代替(ツールなし時) |
|---|---|---|
| シークレット検出(1-1) | gitleaks / trufflehog | Grepでパターン検索(api[_-]?key、password、token、AKIA等の代表パターン+高エントロピー文字列の目視) |
| 静的解析(4-1) | semgrep(言語対応があれば) | Claudeによる全ファイル通読でのインジェクション系パターン検査(その旨を調書に明記) |
| 依存の実在確認(4-2) | npm view / pip index versions で全依存を照会 | レジストリWebページの確認 |
| 既知CVE(4-3) | npm audit / pip-audit / osv-scanner | 主要依存のバージョンをOSV.devで手動照会 |
| ライセンス(5-3) | license-checker等 | package.json/METADATA からライセンス欄を集計 |
| 複製コード(6-1) | jscpd等 | 省略可(未検証面台帳へ) |

すべての実行コマンド・バージョン・生出力の要約を監査調書に記録。指摘には可能な限りCWE番号を併記する。

### Phase 3: Codex独立監査(判断層)

**独立再現モードを厳守する**:Codexに渡すのは仕様書のパスとコードのパスのみ。Claudeによる実装の説明・言い訳・先行レビュー結果は一切渡さない(自己選好バイアス・誘導の排除)。

```
codex exec -m gpt-5.6-sol -c model_reasoning_effort="xhigh" --sandbox read-only --skip-git-repo-check "<監査依頼文>"
```

監査依頼文には以下を含める:
- 役割:「あなたは独立監査人。実装者の説明は与えられていない。仕様書とコードだけから監査せよ」
- 入力:仕様書の絶対パス、コードのルートパス
- 観点:references/audit-standards.md の領域1・2・3・9の判断層項目(依頼文に観点を列挙して渡す。特にネガティブ要件=禁止事項の混入、Excessive Agency=過剰権限、不可逆操作の人間承認、データフローの外部送信経路)
- 出力形式:「指摘ごとに:重大度(Critical/Important/Minor)/該当ファイル:行/内容/業務影響/該当するCWE・OWASP項目(分かる場合)。指摘なしの観点は『指摘なし』と明記」

タイムアウトは10分。Codexの生出力は監査調書に全文記録する。

### Phase 4: 修正ループ

Critical/Important指摘についてClaudeが修正 → `codex exec resume --last -c model_reasoning_effort="xhigh"` で再検証。Critical/Importantがゼロになるまで繰り返す(上限5周。超えたら残指摘を「未修正の理由」付きで報告書に記載)。全ての指摘→修正→再検証の履歴を監査調書に記録。**Minorの扱い**:修正は任意。未修正のMinorは報告書第7章に列挙する。

### Phase 5: 能動的試験(メニューに応じて)

- **逆向き検証(3-4)**(標準以上):代表的な欠陥を1〜3個意図的に混入した検証用ブランチを作り、テストスイートとPhase 2のツールが検出できるか確認。検出できなければ「テストの実効性に疑義」として報告。**検証後は必ずブランチを破棄し、混入コードが本体に残っていないことをdiffで確認する**
- **おとり情報による漏洩試験(1-6)**(厳格、または個人情報を扱うシステム):偽の個人情報・カナリア値を投入して実運転し、ログ・通信・出力ファイルに現れないか確認
- **業務不変条件への連続攻撃(2-6)**(厳格):仕様書から「何が起きても守る条件」を抽出し、Codexに攻撃シナリオ(重複操作・同時実行・日付境界・中断再試行)を生成させて実行
- **受入テスト(3-3)**(全メニュー):webapp-testingスキル(Playwright)で業務シナリオの実動作確認+スクショを `audit/evidence/` に保存。Webでないシステムは実行ログで代替

### Phase 6: 成果物生成と封印

1. templates/ の3雛形から報告書・監査調書・未検証面台帳を生成。**報告書の絶対ルール**は references/audit-standards.md の「報告書執筆ルール」に従う(4値評価・合格率禁止・「参照」表記・限界の開示)
2. 封印:`git rev-parse HEAD` と主要成果物(エントリポイント・設定・lockファイル)の `shasum -a 256` を `seal.json` に記録し、報告書第3章に転記
3. 報告書第9章に**有効期限**を明記:「コード・依存・設定のいずれかが変更された時点で本監査意見は失効し、再監査を要する」
4. ユーザーへの納品報告では、監査意見(稼働可否)と重大指摘の要約を最初に伝える

## 禁止事項(このスキル自身のネガティブ要件)

- 証跡のない「確認済み」記載。実行していない検査を実施済みと書くこと
- 「安全を保証」「ISO準拠」「第三者監査」という言い切り(正しくは「〜を参照した監査」「異系統AIによる独立監査」)
- 合格率・点数による総合評価の表示
- Codexへの実装説明の混入(独立性の毀損)
- 逆向き検証で混入した欠陥コードの残置
- ユーザーの実データ・実際の個人情報をおとり試験に使うこと(必ず架空データを生成する)
