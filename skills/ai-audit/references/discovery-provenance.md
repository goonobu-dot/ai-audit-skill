# 発見の来歴(Discovery Provenance)— なぜ発見できたのかを監査資産にする

出所: 3社会議(Claude・Codex・Grok 独立、2026-08-25)。研究の接地は本文の各項に付す。
目的: 監査の各指摘(finding)に「何を(WHAT)」だけでなく「なぜ発見できたか(WHY/HOW)」を機械可読で残す。これにより、件数でなく「どの独立した認知手順が、どの見落としを実際に破ったか」を再利用可能な監査資産に変える。同時に、その発見が本物か(幻覚でないか)を検証可能にし、能力の誇示でなく誠実さの強化にする。

## 中核の一言(誇張禁止と整合)

「AIにしか見つけられない」は言い過ぎである。本当に効いているのは **認知的独立性(cognitive independence)**——別系統・別手順・実行証拠が、実装者の思い込みを共有していないこと。これが人(および実装者AI)の見落としを破る本質である。よって発見の価値は「AIだから」でなく「独立した認知が実行証拠を突きつけたから」と正確に記述する。

## 監査の観点(lens)とゴール定義

各lensは「何を見て・何をもって発見とするか」を固定する。指摘は必ずいずれかのlensに属する。

| lens_id | 何を見るか / 何を発見とするか |
|---|---|
| `contract` | 仕様突合。文書の必須/禁止と、コード・ゲート・CIが**実際に走ること**が1対1で繋がっているか。未接続・迂回・到達不能=発見 |
| `execution` | 実行証跡。コマンドを走らせ、終了コード・出力・副作用・ログが主張と一致するか。不一致=発見 |
| `exposure` | 秘密・データ境界。秘密/PIIが履歴・成果物・外部送信bundleに生で残らないか(全経路)。漏れ・検出器間の不一致=発見 |
| `authority` | 権限・副作用。読み取り専用監査が書き込み・通信・本番操作へ逸脱していないか。不可逆作用に歯止めがあるか |
| `independence` | 相互独立。実装者説明なしで別系統が同じ欠陥を再検出できるか(できなければ未検証と明示) |

補足: **設定・環境・CI/デプロイ経路**も対象。Replit型事故はソース行でなく実行文脈に出る。

## 人が構造的に見落とす型(human_blindspot の選択肢)

いずれも研究と実務で裏づけのある型。指摘には「人ならどの型で見落とすか」を記録する。

| 値 | 説明 | 接地 |
|---|---|---|
| `story-trust` | 文書と関数が存在すると「実装済み」と脳内補完し、登録・呼び出し・実行経路の欠如を見ない | 本プロジェクトのv1.3配線漏れの実例。レビューの本質は"理解"(Bacchelli & Bird, ICSE 2013) |
| `sampling` | 数行/一部を見て安心し、全母集団を同一基準で洗わない。注意は均等でない | 大差分ほど検出率低下(Cohen 2006 Cisco / Rigby & Bird 2013) |
| `single-tool-trust` | 「gitleaks緑」で打ち切り、別検出器・別ヒューリスティックで交差しない | 単一パスの限界(Edmundson 2013: 平均発見率33%、経験は予測にならない) |
| `negative-evidence` | 「呼ばれていない」「検査対象外」「失敗時処理がない」は差分に現れず見えにくい | レビュー欠陥の約75%は実行時でなく保守性(Mäntylä & Lassenius, TSE 2009) |

## 認知的独立性が発見できる機序(why_found の選択肢)

| 値 | 機序 |
|---|---|
| `assumption-free` | 実装者の「繋いだはず」を継承せず、文書上の約束から登録点・呼び出し・出力まで辿る |
| `uniform-sweep` | 禁止事項・要求ID・必須経路を全ファイル/スクリプト/CI設定へ同一基準で機械的総当たり。一件だけの例外を拾う |
| `full-context` | 差分と周辺を同時に保持し、「宣言↔呼び出し↔ゲート登録」の欠落辺を辿る |
| `evidence-conflict` | ソース/生成物/実行結果/複数検出器を並べ、「gitleaks陰性だが別検出器は陽性」等の不一致を欠陥候補にする |
| `execution-proof` | 実際に動かし、主張と実測(終了コード・出力・副作用)の食い違いを突く |

## AIが弱い点(誠実な線・記録に反映する)

- **暗黙の業務意図・妥当性**: 本番挙動・UX意図・規制の「妥当か」は、コードと明文資料だけでは正誤を決められない → `finder_class` を安易に `ai_cross` にせず、判断に人間が要る旨を残す。
- **観測できない環境+捏造リスク**: 本番権限・秘密・外部状態・希少な競合は再現できない。仕様が曖昧だと「ありそうな欠陥」を幻覚しやすい。→ **証拠コマンド(reproduction)のない指摘は信頼しない**。裏づけとしてAnthropic自身が「Claudeは貧弱なQAエージェント/自分の指摘を大したことないと自分を納得させる」と明言(harness-design blog)、LLM評価者の自己選好バイアス(別系統評価で緩和)。

## finding ごとに記録する来歴スキーマ

> **正直な但し書き(3社会議2026-08):これらは現状「自己申告の手書きメタデータ」であり、機械検証はまだ実装していない。** `validate-report`/`validate-bundle` は結論・証拠hash・禁止表現は検査するが、来歴5項目のschema・enum・reproductionの実在までは検査しない。したがって「必須」はレビュー運用上の規律であって機械強制ではない。`finder_class=ai_cross` の件数を「独自価値の証明」や「安全の根拠」に読み替えないこと。将来、findingをJSON schema化してvalidatorに接続するまでは、来歴は"どう発見したかの申告"に留まる。

**core(記録する5項目・運用上必須)**: `lens_id` / `why_found` / `human_blindspot` / `finder_class` / `reproduction`
**extended(任意)**: `claim_checked` / `evidence_seen` / `observation` / `detection_op` / `independence`

| フィールド | 内容 | 必須 |
|---|---|---|
| `lens_id` | contract / execution / exposure / authority / independence | ◎ |
| `why_found` | 機序タグ(assumption-free / uniform-sweep / full-context / evidence-conflict / execution-proof) | ◎ |
| `human_blindspot` | 人が落とす型(story-trust / sampling / single-tool-trust / negative-evidence / none) | ◎ |
| `finder_class` | `ai_cross`(認知的独立でのみ) / `ai_or_human`(人でも可) / `tool_only`(機械検出器) | ◎ |
| `reproduction` | 第三者が再現できる最小コマンド・入力・期待/実測。無ければ指摘の信頼度を下げる | ◎ |
| `claim_checked` | 検証した仕様文・禁止事項・不変条件を一文で | ○ |
| `evidence_seen` | 確認した file:行・設定キー・コマンド・入力・検出器 | ○ |
| `observation` | 実測(exit code・差分・未登録パス等)。期待と観測を対で | ○ |
| `detection_op` | 実際の操作:経路追跡 / 全文走査 / 総当たり突合 / 実行 / 検出器比較 | ○ |
| `independence` | 実装者と同一モデルか別系統か。指示・検出器・証拠を共有したか | ○ |

## 集計と使い方

- `finder_class = ai_cross` の件数=「認知的独立性でのみ見つかった指摘」。これはこの監査の独自価値の本体であり、報告書で別掲する。ただし「AIすごい」でなく「独立した認知が破った見落とし」と表現する。
- `human_blindspot` の分布=このコードで人が最も落としやすい型。次回のレビュー観点の優先度づけに使える。
- `reproduction` の無い指摘=幻覚の可能性。core必須なので、無い指摘は「未検証の疑い」として重大度を上げない。

## 濫用しないための線

- 来歴は「なぜ本物か」を示すための記録であって、`finder_class=ai_cross` を増やすことが目的ではない。人でも見つかるものを ai_cross と誇張しない。
- 発見件数・来歴の充実を「安全の保証」に読み替えない。未検証面台帳・限界の開示は従来どおり優先する。
