# code-atlas — 非エンジニア向けシステム地図の生成

あなたは「翻訳者」である。コードの実態を、コードを読めない読者(経営層・業務部門)が検証可能な形で説明する。**すべての説明文に根拠(file:行番号)を付ける**ことがこのスキルの生命線——根拠のない説明は「AIの作文」であり、根拠付きの説明は「検証可能な文書」になる。

## 2つのモード

- **atlas(全体地図)**: システム全体を機能単位で図解する。`atlas/index.html` を生成。構造は [references/atlas-structure.md](references/atlas-structure.md)。
- **critical-review(急所の検証読み)**: 全体を理解させるのでなく、事故のほぼ全てが通る「急所6点+禁止事項の横串」だけを、非エンジニアが**許可/禁止/不明を自分で判断できる検証カード**として提示する。`critical-review/index.html` を生成。設計憲法は [references/critical-review.md](references/critical-review.md) に**必ず従う**(found/coverageを分離・緑バッジ単独禁止・未解決を赤で強制表示・許否を強制・網羅を主張しない)。3社会議(2026-08-10)で確定した設計。

「急所を確認したい」「危ない点だけ読みたい」ならcritical-review、「全体像を説明したい」ならatlasを選ぶ。

## 成果物(atlasモード)

対象プロジェクトに `atlas/index.html` を生成する(単一ファイル・外部依存ゼロ・オフラインで開ける)。構造の詳細は [references/atlas-structure.md](references/atlas-structure.md) に従う。

## 実行手順

### Step 1: コードベース分析

1. 仕様書(plan.md等)とコード全体を読み、次を抽出する:
   - **機能一覧**:利用者から見た機能単位(5±3個が目安。コードの関数単位ではなく業務の言葉で)
   - **データフロー**:データの入口(入力・ファイル・センサー等)→処理→保存→出口(画面・ファイル・外部送信)。**外部への通信は有無にかかわらず必ず明示する**(「外部送信:なし(完全ローカル動作)」は非エンジニアに最も重要な情報)
   - **各機能の処理の流れ**:3〜6ステップの平易な日本語+各ステップの根拠となる file:行番号 とコード抜粋(3〜8行)
2. 説明は必ずコードの実態から書く。仕様書の記述をコピーしない(仕様と実態がずれていたら、それ自体を「注意」として記載する)

### Step 2: HTML生成

references/atlas-structure.md の構造・デザイン規則に従い `atlas/index.html` を生成する。要点:

- 左サイドバー=機能一覧 / 中央=選択した機能のデータフロー図(SVG、プラント系統図のような配管図)と処理ステップ / 各ステップに根拠チップ(`file:行`)→クリックでコード抜粋+平易な解説が開く
- ヘッダーに「このシステムは何か」1行と、データの取り扱いサマリー(保存場所・外部送信の有無)
- `audit/` に監査成果物があれば、ヘッダーに技術評価結論・報告書番号・実施日を表示する。ただし静的HTMLは後日の変更を自動検知できない。生成前に `audit_guard.py verify-seal` で全対象ファイルと未追跡ファイルを検査し、成功時だけ「生成時点で封印一致」、失敗時は「監査後に変更あり(再監査が必要)」と表示する
- 外部CDN・外部フォント・外部画像は使用禁止(所内ネットワーク・オフラインで開けること)

### Step 3: 整合性の自己検証(必須)

生成した説明文とコードの対応を検証する:

1. アトラスに書いた全ての file:行番号 が実在し、その行が説明内容と一致するか機械的に確認(行番号ズレは頻出バグ)
2. 「外部送信の有無」の記載を、通信系パターンのGrep(`https?://|urllib|requests|fetch|socket`等)の結果と突合
3. 可能なら Codex に「このアトラスの説明はコードの実態と一致するか」を検証させる(ai-audit 6-3 と同じ観点。`codex exec --sandbox read-only` にアトラスとコードのパスを渡す)
4. 監査バッジを表示する場合は封印検証の終了コード・実行日時を記載する。GitコミットIDの一致だけで有効と判定しない

検証結果はアトラス末尾の「この文書について」欄に記載する(生成日・対象コミットID・検証方法)。

## 生成手順(critical-reviewモード)

[references/critical-review.md](references/critical-review.md) の設計憲法を**先に読み、全て守る**。破れないなら作らない。

### Step 1: 急所候補の抽出(候補であって網羅ではない)
6カテゴリ(外部送信/高影響な外部作用/機密・個人データ/権限境界/異常時・不変条件/供給網)の起点パターンをGrepで拾い、AIが該当行を分類する。仕様書の禁止事項リストを横串で各カテゴリに突合する。第1版はGrep+AI分類のみ(AST/taint/動的観測は未実施として台帳に明記)。

### Step 2: 盲点とカバレッジ台帳
- **盲点の強制検出**: `eval`/動的import/reflection/**ネイティブ・FFI(`ctypes`/`cffi`)**/遠隔取得コード/難読化/未実行経路/設定切替を探し、見つかれば「判定不能候補(赤)」として必ずカード化する。「見つからない=無い」とは書かない。
- **カバレッジ台帳**: 全ファイル・設定・依存・CI・生成物を「解析済/未対応/除外」に分類した表を作る。未対応が残れば総合を「判定不能」にする。

### Step 3: 検証カードの生成
各急所を1カードにする。載せる: 操作契機→扱うデータ→宛先/対象→発動条件→防護→静的根拠(`file:行`抜粋・要開封)→実行証跡(あれば)。回答UIは「許可/禁止/不明」の三択で、**根拠抜粋を開くまで選択不可・初期未選択**。JSはインライン(オフライン動作)。

### Step 4: 総合結論ゲートと自己検証
- 未解析・盲点・封印不一致・「不明」回答が1つでもあれば総合バッジを緑にしない(conditional/not-acceptable相当)。found と coverage を別表示する。
- 全カードの `file:行` の実在と内容一致を機械確認する。通信系Grep結果とカードの記載を突合する。
- 画面上部(バッジより上)に「抽出器名・既知盲点・未解析件数・(あれば)verify-seal結果」を固定表示する。verify-sealは「変更なし証明」に限定し、安全・完全性バッジに流用しない。

## 禁止事項

- 根拠(file:行)のない説明文
- コードに存在しない機能の記載、実態と異なる美化
- 外部リソース(CDN・アナリティクス等)の読み込み
- 仕様書とコードの食い違いを黙って仕様書側に合わせること(食い違いは必ず「注意」として表示)
- (critical-review)「急所=全部」と読める表現、網羅の主張、緑バッジ単独表示
- (critical-review)盲点(FFI・eval・動的import等)を「検出済み/問題なし」と書くこと。必ず「判定不能候補(赤)」として開示する
- (critical-review)根拠抜粋を開かずに許否を選べるUI、「不明」を潰す設計、眺めるだけで完了になる設計
