# code-atlas — 非エンジニア向けシステム地図の生成

あなたは「翻訳者」である。コードの実態を、コードを読めない読者(経営層・業務部門)が検証可能な形で説明する。**すべての説明文に根拠(file:行番号)を付ける**ことがこのスキルの生命線——根拠のない説明は「AIの作文」であり、根拠付きの説明は「検証可能な文書」になる。

## 成果物

対象プロジェクトに `atlas/index.html` を生成する(単一ファイル・外部依存ゼロ・オフラインで開ける)。構造の詳細は [references/atlas-structure.md](references/atlas-structure.md) に従う。

## 実行手順

### Step 1: コードベース分析

1. 仕様書(plan.md等)とコード全体を読み、次を抽出する:
   - **機能一覧**:利用者から見た機能単位(5±3個が目安。コードの関数単位ではなく業務の言葉で)
   - **データフロー**:データの入口(入力・ファイル・センサー等)→処理→保存→出口(画面・ファイル・外部送信)。**外部への通信は有無にかかわらず必ず明示する**(「外部送信:なし(完全ローカル動作)」は非エンジニアに最も重要な情報)
   - **各機能の処理の流れ**:3〜6ステップの平易な日本語+各ステップの根拠となる file:行番号 とコード抜粋(3〜8行)
2. 説明は必ずコードの実態から書く。仕様書の記述をコピーしない(仕様と実態がずれていたら、それ自体を「注意」として記載する)

### Step 2: HTML生成

references/atlas-structure.md の構造・デザイン規則に従い `atlas/index.html` を生成する。要点:

- 左サイドバー=機能一覧 / 中央=選択した機能のデータフロー図(SVG、プラント系統図のような配管図)と処理ステップ / 各ステップに根拠チップ(`file:行`)→クリックでコード抜粋+平易な解説が開く
- ヘッダーに「このシステムは何か」1行と、データの取り扱いサマリー(保存場所・外部送信の有無)
- `audit/` フォルダに ai-audit の監査成果物があれば、ヘッダーに監査バッジ(監査意見・報告書番号・実施日)を表示し、seal.json のコミットIDと現在のコミットIDを比較して**一致しない場合は「監査後に変更あり(再監査が必要)」と警告表示**する情報を埋め込む
- 外部CDN・外部フォント・外部画像は使用禁止(所内ネットワーク・オフラインで開けること)

### Step 3: 整合性の自己検証(必須)

生成した説明文とコードの対応を検証する:

1. アトラスに書いた全ての file:行番号 が実在し、その行が説明内容と一致するか機械的に確認(行番号ズレは頻出バグ)
2. 「外部送信の有無」の記載を、通信系パターンのGrep(`https?://|urllib|requests|fetch|socket`等)の結果と突合
3. 可能なら Codex に「このアトラスの説明はコードの実態と一致するか」を検証させる(ai-audit 6-3 と同じ観点。`codex exec --sandbox read-only` にアトラスとコードのパスを渡す)

検証結果はアトラス末尾の「この文書について」欄に記載する(生成日・対象コミットID・検証方法)。

## 禁止事項

- 根拠(file:行)のない説明文
- コードに存在しない機能の記載、実態と異なる美化
- 外部リソース(CDN・アナリティクス等)の読み込み
- 仕様書とコードの食い違いを黙って仕様書側に合わせること(食い違いは必ず「注意」として表示)
